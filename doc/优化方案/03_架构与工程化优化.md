## 一、模块边界：从 9 目录到清晰分层

### 1.1 现状边界问题

`src` 现有 9 目录：ai / agent / theme / shortcuts / notifications / components / interactions / styles / shared（`list_dir` 实测）。边界混乱点：

- **`shared/` 是个杂物抽屉**：同时含主题（`ThemeContext.tsx`，与 `theme/` 重复）、令牌（`designTokens.ts`，与 `styles/` 重复）、布局组件（`AppShell`/`Omnibar`/`TabsBar`）、状态组件（`States.tsx` 的 EmptyState，与 `components/UIDesignSystem` 重复）、快捷键 hook（`useKeyboardShortcuts.tsx`，与 `shortcuts/` 重复）——一个目录横跨 4 个职责域。
- **`styles/` vs `shared/designTokens` vs `components/UIDesignSystem`**：三处令牌（[01 A-5](./01_现状审计与问题清单.md)）。
- **`interactions/`**：仅 `interactionPatterns.ts` 一文件，且核心导出 `InteractionFeedback` 是空实现（[01 A-9](./01_现状审计与问题清单.md)），是否值得独立模块存疑。

### 1.2 推荐模块划分（唯一方案）

按"**能力域**"而非"文件类型"重组，明确 8 个公共子路径 + 内部私有目录：

| 目标模块 | 子路径 | 内容 | 来源合并 |
|----------|--------|------|----------|
| `ai` | `z-biz-tool-shared/ai` | AIManager/AIConfig/ContextManager | 现 `src/ai/` |
| `agent` | `z-biz-tool-shared/agent` | AgentManager/AgentPanel/SQLEditor/QueryHistoryViewer + `AgentService` 注入接口 | 现 `src/agent/` |
| `theme` | `z-biz-tool-shared/theme` | **唯一主题系统**：合并 `src/theme/` + `src/shared/ThemeContext.tsx`（明暗作为 theme 的 mode 维度） | theme + shared/ThemeContext |
| `shortcuts` | `z-biz-tool-shared/shortcuts` | **唯一快捷键系统**：合并 `src/shortcuts/` + `src/shared/useKeyboardShortcuts.tsx` + `src/components/GlobalShortcutHandler.tsx` | 三处合一 |
| `notifications` | `z-biz-tool-shared/notifications` | toastManager/ToastContainer | 现 `src/notifications/` |
| `components` | `z-biz-tool-shared/components` | 轻量 UI（UIDesignSystem 11 组件）+ 布局（AppShell/Omnibar/TabsBar/DragHandle/CollapsiblePanel/Navbar/Spotlight） | components + shared 布局组件 |
| `tokens` | `z-biz-tool-shared/tokens` | **唯一令牌源**（[02 §4](./02_API设计与开发者体验.md)） | styles/designTokens + shared/designTokens + UIDesignSystem.DESIGN_TOKENS |
| `styles` | `z-biz-tool-shared/styles` | globalStyles（CSS 字符串）+ ThemeStyles | 现 `src/styles/globalStyles` + theme/ThemeContext 的样式注入 |

**取消的目录**：`shared/`（内容分流到 theme/shortcuts/components/tokens）、`interactions/`（`INTERACTION_PATTERNS`/`USER_FLOWS` 等纯常量规范并入 `tokens` 或降级为文档，空实现 `InteractionFeedback` 从公共 API 移除直至有真实实现）。

原则：**每个子路径 = 一个内聚能力域 = 一个可独立 tree-shake 的单元**。跨域引用只能从高阶域指向低阶域（如 components→tokens/theme，禁止 tokens→components）。

## 二、构建工具与产物格式（唯一推荐）

### 2.1 推荐 tsup 产出 ESM + CJS + d.ts

现状**无构建**（[01 A-1/A-2](./01_现状审计与问题清单.md)），下游被迫直连 TS 源码或复制。推荐引入 **tsup**（esbuild 驱动，零配置产出多格式 + `.d.ts`，是 TS 库社区主流，对标其理念）：

```jsonc
// package.json scripts —— 规划新增
{
  "scripts": {
    "build": "tsup",
    "dev": "tsup --watch",
    "typecheck": "tsc --noEmit",
    "lint": "eslint src --ext ts,tsx",
    "clean": "rm -rf dist"
  }
}
```

```ts
// tsup.config.ts —— 规划新增
import { defineConfig } from 'tsup';
export default defineConfig({
  entry: {
    index: 'src/index.ts',
    ai: 'src/ai/index.ts',
    agent: 'src/agent/index.ts',
    theme: 'src/theme/index.ts',
    shortcuts: 'src/shortcuts/index.ts',
    notifications: 'src/notifications/index.ts',
    components: 'src/components/index.ts',
    tokens: 'src/tokens/index.ts',
    styles: 'src/styles/index.ts',
  },
  format: ['esm', 'cjs'],       // 双格式
  dts: true,                     // 生成 .d.ts
  splitting: true,               // ESM 代码分割，利于 tree-shaking
  treeshake: true,
  external: ['react', 'react-dom', 'antd', '@ant-design/icons', 'zustand', '@uiw/react-codemirror'],
  sourcemap: true,
  clean: true,
});
```

### 2.2 产物格式决策

| 决策点 | 推荐 | 理由 |
|--------|------|------|
| 格式 | **ESM 为主 + CJS 兜底** | 下游全是 vite（ESM）；保留 CJS 兼容潜在 node 侧脚本/测试 |
| `.d.ts` | **必产**，随每个 entry | 下游 `tsc --noEmit` 需要类型（解决 [01 A-2](./01_现状审计与问题清单.md)） |
| `module`/`main`/`types` | `main`→CJS，`module`→ESM，`types`→d.ts，`exports` 分条件 | 见 §4 |
| external | react/antd/zustand 等**全部 external**，不打包进产物 | 避免下游双实例（见 §3、[01 H-2](./01_现状审计与问题清单.md)） |
| sourcemap | 产出 | 便于下游调试库代码 |

### 2.3 tsconfig 修正

现状 tsconfig 矛盾（[01 A-2](./01_现状审计与问题清单.md)）。推荐：**tsconfig 只用于 typecheck（`noEmit:true`），产物完全交给 tsup**，移除 `composite`/`declaration`/`declarationMap`/`outDir`（这些由 tsup 的 dts 负责）。`strict` 分阶段开启（见 §6）。

## 三、依赖治理（唯一推荐）

### 3.1 dependencies → peerDependencies

现状 react/antd/zustand/immer/codemirror 全在 `dependencies`（[`../../package.json:12-20`](../../package.json)）。**库不应把宿主框架锁进自己的 dependencies**，否则下游各装一份 → 双 React/双 antd 实例 → hooks 崩溃。推荐：

```jsonc
// package.json —— 规划目标
{
  "peerDependencies": {
    "react": ">=18 <20",
    "react-dom": ">=18 <20",
    "antd": ">=5 <7",
    "@ant-design/icons": ">=5 <7",
    "zustand": ">=4 <6"
  },
  "peerDependenciesMeta": {
    "antd": { "optional": true },              // components/tokens 子路径不强制 antd
    "@ant-design/icons": { "optional": true },
    "@uiw/react-codemirror": { "optional": true }
  },
  "devDependencies": {
    "react": "^19.0.0", "antd": "^6.0.0", "zustand": "^5.0.0",  // 本地开发/测试用
    "tsup": "^8", "typescript": "^5.7.0", "vitest": "^2", "@testing-library/react": "^16"
  }
}
```

要点：① 宿主框架（react/antd/zustand）→ peer，且给**宽松范围**兼容下游不同版本（pet 用 antd `^6.5.3`、其余 `^6.0.0`，见 [01 下游表](./01_现状审计与问题清单.md)）；② antd/icons/codemirror 标 **optional peer**，让 `components`/`tokens` 等无 antd 依赖的子路径能被纯 React 项目使用；③ devDependencies 保留一份用于本地构建与测试。

> 注：HEAD 提交信息"dedupe react/antd/codemirror from peerDependencies into shared consumers"显示维护者曾把依赖从 peer 挪向 consumers——方向与本篇推荐相反，需在 [04](./04_稳定性兼容与发布安全.md) 兼容策略中确认最终形态，避免反复。

### 3.2 幽灵依赖清理

`immer`（[`../../package.json:14`](../../package.json)）与 `@uiw/react-codemirror`/`@codemirror/lang-sql`（L18-19）在 `src` 中**零引用**（`grep immer|codemirror src examples` 实测无结果）。SQLEditor 已注明"无外部编辑器依赖"（[`../../src/agent/SQLEditor.tsx:1`](../../src/agent/SQLEditor.tsx)）。推荐：**从 dependencies 移除 immer 与两个 codemirror 包**（除非后续 SQLEditor 真要用 codemirror，届时再作为 optional peer 引入）。减少下游安装体积与供应链面。

### 3.3 依赖版本策略

- peer 用**范围**（`>=18 <20`）而非精确版，兼容下游漂移；
- dev 用**精确 minor**（`^19.0.0`）保证本地可复现；
- 锁文件 `package-lock.json` 存在（112KB），保留用于本地开发一致性，但**发布产物不含 node_modules**（见 [04 §5](./04_稳定性兼容与发布安全.md)）。

## 四、package.json exports 与 dist 策略（唯一推荐）

### 4.1 exports 映射

```jsonc
// package.json —— 规划目标
{
  "name": "z-biz-tool-shared",
  "version": "0.1.0",
  "type": "module",
  "main": "./dist/index.cjs",
  "module": "./dist/index.js",
  "types": "./dist/index.d.ts",
  "exports": {
    ".":               { "types": "./dist/index.d.ts",  "import": "./dist/index.js",  "require": "./dist/index.cjs" },
    "./ai":            { "types": "./dist/ai.d.ts",     "import": "./dist/ai.js",     "require": "./dist/ai.cjs" },
    "./agent":         { "types": "./dist/agent.d.ts",  "import": "./dist/agent.js",  "require": "./dist/agent.cjs" },
    "./theme":         { "types": "./dist/theme.d.ts",  "import": "./dist/theme.js",  "require": "./dist/theme.cjs" },
    "./shortcuts":     { "types": "./dist/shortcuts.d.ts","import":"./dist/shortcuts.js","require":"./dist/shortcuts.cjs" },
    "./notifications": { "types": "./dist/notifications.d.ts","import":"./dist/notifications.js","require":"./dist/notifications.cjs" },
    "./components":    { "types": "./dist/components.d.ts","import":"./dist/components.js","require":"./dist/components.cjs" },
    "./tokens":        { "types": "./dist/tokens.d.ts", "import": "./dist/tokens.js", "require": "./dist/tokens.cjs" },
    "./styles":        { "types": "./dist/styles.d.ts", "import": "./dist/styles.js", "require": "./dist/styles.cjs" },
    "./package.json":  "./package.json"
  },
  "files": ["dist"],
  "sideEffects": ["**/*.css", "./dist/styles.js"]
}
```

### 4.2 关键决策

| 决策 | 推荐 | 理由 |
|------|------|------|
| `exports` 子路径 | **每模块一条**，禁止 `./src/*` 通配 | 杜绝现状 file 项目的 `z-biz-tool-shared/src/...` 深路径反模式（[01 §二](./01_现状审计与问题清单.md)） |
| `files` | **`["dist"]`** | 发布只带产物，源码/examples/doc 不入包（减小体积、避免泄漏，见 [04 §5](./04_稳定性兼容与发布安全.md)） |
| `sideEffects` | 标注 CSS/styles 有副作用，其余 false | 让打包器安全 tree-shake 未用模块 |
| dist 是否入 git | **不入**（保持 `.gitignore` 现状 `dist/`，[`../../.gitignore`](../../.gitignore)） | 产物由 CI 构建；但 file-link 集成需下游能触发构建（见 §5） |

## 五、下游集成方式（唯一推荐）

现状是 `file:../z-biz-tool-shared` 符号链接直连源码（[01 §二](./01_现状审计与问题清单.md)）。三种主流方式对比后**推荐分阶段演进**：

| 方式 | 适用阶段 | 决策 |
|------|----------|------|
| **A. `file:` link + 库预构建 dist** | 近期（阶段1-4） | ✅ **推荐起步**：保留 `file:` 便于本地联调，但下游改为消费 `dist`（经 exports），不再直连 src。库需 `npm run build` 后下游才拿到最新产物（配 watch） |
| **B. npm/pnpm workspaces** | 中期（阶段5+） | ✅ **推荐终态**：把 z-biz-tool 系列纳入单一 workspace（根 `package.json` + `workspaces:["z-biz-tool-*"]`），依赖提升、版本统一、`tsc` project references 天然可用。当前仓库已有根 `package-lock.json`/`package-all.sh` 雏形，具备迁移基础 |
| **C. 发布私有 registry（verdaccio/npm 私仓）** | 远期可选 | ⚠️ 仅当需要跨仓库/跨机器分发时才上；当前单仓多包场景 workspace 更轻 |

**明确不推荐**：继续直连 `src`（现状）。它绕过包契约、依赖下游各自 vite 编译 node_modules 内 TSX（[01 H-1](./01_现状审计与问题清单.md) 未验证但风险高）、且无法产出 d.ts。

file-link 的"提交即影响下游"风险与缓解见 [04 §2](./04_稳定性兼容与发布安全.md)。

## 六、tree-shaking 与类型质量工程化

### 6.1 tree-shaking 保障

- ESM 产物 + `sideEffects` 标注（§4.2）+ tsup `splitting/treeshake`（§2.1）三者合力；
- **子路径拆分本身即最强 tree-shaking**：下游 `import { toastManager } from 'z-biz-tool-shared/notifications'` 只拉通知模块，不碰 antd 依赖的 theme/components；
- 避免顶层 `index.ts` 副作用导入（现状 [`../../src/index.ts`](../../src/index.ts) 是纯 re-export，良好，需保持）。

验收：下游按需引单个子路径时，bundle 不含 antd/codemirror（当这些子路径不依赖它们时），见 [06 bundle 指标](./06_测试验收与风险清单.md)。

### 6.2 strict 模式分阶段开启

现状 `strict:false`（[`../../tsconfig.json:14`](../../tsconfig.json)）。一次性开 strict 会产生大量报错阻塞。推荐分阶段：

1. 先开 `strictNullChecks`（收益最大、破坏可控），修复暴露的 null 问题；
2. 再开 `noImplicitAny`，配合消除 8 处 any（[02 §3.1](./02_API设计与开发者体验.md)）；
3. 最后 `strict:true` 全量 + `noUnusedLocals`/`noUnusedParameters`（现状均 false，[`../../tsconfig.json:15-16`](../../tsconfig.json)）。

每阶段以 `tsc --noEmit` 零错误为门槛，纳入 CI（见 [06](./06_测试验收与风险清单.md)）。

### 6.3 类型导出完整性工程化

- 引入 `api-extractor`（或 tsup 的 dts 汇总）生成**单一 `.d.ts` bundle + API 报告文件**（`api-report/*.api.md`），把导出面固化进仓库；
- CI 中 diff API 报告，导出面变化必须显式提交 → 破坏性变更无处遁形（联动 [04 §3](./04_稳定性兼容与发布安全.md)）。
