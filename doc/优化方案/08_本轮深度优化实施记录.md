## 二、T5.6：AI 能力补全（A-10 / A-11）

台账 05 T5.6 原文：「`src/ai/AIManager.ts`：落地 timeout/AbortController（01 A-10）、
provider 工厂真实分支或明确单一 provider（01 A-11）；审计 console 不泄漏 apiKey（04 §5.2）」。

### 2.1 根因：客户端实现与工厂长在同一个文件里，导致「两处必须一致」没人守

改动前 `src/ai/AIManager.ts` 里同时住着 `AIClient` 接口、`OpenAIClient` 类和
`createClient` 工厂。三件事纠缠在一起：

- 工厂的 `switch (config.provider)` 只有 `case 'openai'` 一个真分支，
  `'claude' | 'gemini' | 'ollama' | 'local'` 全部落进 `default` **返回 OpenAIClient**；
- `OpenAIClient` 里 `fetch` 从不带 `AbortController`，
  而 `AIConfig.timeout` 声明了、默认还给了 `30000`；
- `executeWithAgent` 把 `provider` 硬编码成 `'local'` ——
  而 `'local'` 在工厂里也落进 default 分支拿 OpenAIClient。

**这三处叠加的实际后果**：配置写 `provider: 'claude'`、模型写 `claude-sonnet-4`，
请求实际打向 `https://api.openai.com/v1/chat/completions`，拿着 Claude 的模型名去问 OpenAI ——
必然 404。**配置说一套、实际做另一套**，调用方从返回的报错里根本看不出是哪配错了。

### 2.2 改法：拆出 `src/ai/clients.ts`，每个 provider 一套协议

| provider | 协议 | 端点 | 鉴权头 | 请求体形状 |
|---|---|---|---|---|
| `openai` | OpenAI | `{base}/chat/completions` | `Authorization: Bearer` | `messages[]` |
| `claude` | Anthropic Messages | `{base}/messages` | `x-api-key` + `anthropic-version` | `system` 独立字段 + `messages[]` |
| `gemini` | Google generateContent | `{base}/models/{model}:generateContent` | `?key=` 之外的请求体 | `contents[].parts[]` + `systemInstruction` |
| `ollama` | OpenAI 兼容 | `http://localhost:11434/v1/...` | 可选 | `messages[]` |
| `local` | OpenAI 兼容 | **必须显式给 `baseUrl`** | 可选 | `messages[]` |

两个刻意的设计决定：

1. **`local` 不猜默认地址**。`'local'` 在仓里从来没被定义过（可能是 ollama、
   也可能是 LM Studio / vLLM）。猜错的话请求会打到一个不存在的端口，
   报出来的错比「没配 baseUrl」难懂得多。现在**明确报错**。
2. **未知 provider 明确报错，不静默回落成 OpenAI**。静默回落正是要治的病。

### 2.3 timeout 真正落地（A-10）

`BaseAIClient.request()` 统一处理超时：

```ts
const controller = new AbortController();
const timer = setTimeout(() => controller.abort(), timeout);
try {
  return await this.fetchImpl(url, { ...init, signal: controller.signal });
} catch (error) {
  if (controller.signal.aborted) {
    throw new Error(`请求超时（${timeout}ms）`);
  }
  throw error;
} finally {
  clearTimeout(timer);
}
```

超时与其它错误**能区分开** —— fetch 抛的 `AbortError` 是个含义模糊的报错，
这里翻译成「请求超时（30000ms）」。`timeout <= 0` 表示显式关闭上限（不注入 signal）。

### 2.4 `executeWithAgent` 的语义矛盾

改前：

```ts
const agentConfig: AIConfig = { ...get().config, modelName: agent.model, provider: 'local' };
```

`'local'` 在工厂里落进 default 分支拿 OpenAIClient ⇒「用 Agent 自己的模型」
实际是「用 OpenAI 的端点 + Agent 的模型名」。改后 provider **沿用全局配置**，
只覆盖 `modelName` —— 这才是这句话的字面含义（`Agent` 类型里本来也没有 provider 字段）。

### 2.5 fetch 可注入（测试与生产都需要）

新增 `setFetchImplementation(impl)`，返回一个还原函数。

**为什么不在测试里猴补 `globalThis.fetch`**：那会污染全局状态，别的测试文件受影响；
而这个注入口对下游也有用（Tauri 后端 / Node 脚本可以塞带代理、带重试的实现）。
实测：改前测试若直接调 `useAIManager.getState().executeAI()`，会**真的发出网络请求**
（实测卡满 10.5s 才因超时失败）—— 06 §1.1 的「绝不发真实 API 请求」铁律要求这个注入口。

## 三、T5.7：通知健壮性（A-12）

### 3.1 三个子问题

| 问题 | 原实现 | 后果 | 修法 |
|---|---|---|---|
| id 可能碰撞 | `Math.random().toString(36).substring(2,9)` | 碰撞时**一个 `removeToast` 干掉两个 toast** | 自增计数器 `toast-${seq}` |
| 定时器句柄丢失 | `setTimeout(...)` 返回值直接丢 | toast 提前移除后回调仍在跑 | 按 id 记进 `Map` |
| `clearToasts` 不清定时器 | 只 `set({toasts: []})` | 清空后每个到点的回调仍会跑一次 `removeToast` | 清定时器 + 清 map |

### 3.2 顺带发现并修掉的隐性缺陷：duration 默认值被 `undefined` 吞掉

原实现：

```ts
const fullToast: ToastConfig = { id, duration: 3000, ...toast };
```

**展开顺序把默认值吃掉了**：当 `toast.duration` 是 `undefined` 时，
展开会把它**覆盖到** `3000` 上面 → `fullToast.duration === undefined`
→ `if (fullToast.duration)` 为假 → **自动消失整个失效，toast 永远挂在屏幕上**。

而 `toastManager.success(message, duration?)` 恰恰就是 `duration: undefined` 这条路径 ——
也就是说**四个便捷方法全都命中了这个缺陷**。

改成 `const duration = toast.duration ?? 3000;`（先取值再展开，不再靠展开顺序）。

## 四、A-8 / A-14：主题

### 4.1 ThemeSelector 是死代码（A-8）

原实现的 `onClick` 调的是 `setModeInternal` —— 一个
`const [, setModeInternal] = useState(mode)` 的 setter，**它改的 state 从来没被读取过**
（解构第一个位置是空位）。于是「跟随系统 / 亮色模式 / 深色模式」三个选项**点了都没反应**。

改法：context 暴露 `setPreference`，`ThemeSelector` 直接调它。

### 4.2 引入了第三态：'system'（跟随系统）

原 `useTheme()` 只有 `mode`（light/dark）+ `toggle`，**无法表达「跟随系统」** ——
而 ThemeSelector 里明明有「跟随系统」这个选项（点了却什么也没发生）。

现在 context 暴露：

- `mode: 'light' | 'dark'` —— 实际生效的模式；
- `preference: 'system' | 'light' | 'dark'` —— 用户的偏好；
- `setPreference(p)` —— 设置偏好。

`toggle` 的语义相应调整：从 `'system'` 出发时，下一次应切到**当前实际模式的反面**
（而不是固定的 dark），否则在浅色系统上点一下会突兀地跳到暗色。

### 4.3 纯逻辑单独成文件（为什么不是 .tsx）

仓库测试跑在 `node --experimental-strip-types` 上，而 **Node 只擦除类型、不转译 JSX**
⇒ `.tsx` 没法被 import。凡是要被单测覆盖的判定逻辑都必须落在 `.ts` 里，
React 组件只做薄封装。故新增 `src/theme/themeMode.ts`（纯逻辑）与
`src/shared/errorMessage.ts`（错误消息归一）。

### 4.4 localStorage 键统一（A-14）

原状：主题有两个键 —— `themeManager` 用通用名 `'theme'`，
`shared/ThemeContext` 用 `'z-tool-theme-mode'`。`'theme'` 这种通用键在同源多应用下会互相覆盖。

改为 `'z-biz-tool-theme-name'` / `'z-biz-tool-theme-preference'`，并做**一次性迁移**：
读新键没有就读旧键，命中则写回新键并删掉旧键。

**迁移的一个坑**：旧键存的是两态（`'light'`/`'dark'`），新键是三态。
读旧键时只能认 `'light'`/`'dark'` 两个值 —— 实现第一版写成了
`legacy === 'dark' ? 'dark' : 'light'`，**把任意非法值都兜成了 `'light'`**，
被测试当场咬住（`tests/theme-mode.test.ts` 的「旧键存的是非法值」用例）后改正。

### 4.5 顺带修：`updateTheme` 的浅合并 bug

`updateTheme(theme: Partial<ThemeConfig>)` 原实现是 `{...state.themeConfig, ...theme}` ——
浅合并。`colors` 是嵌套对象，调用方只想改一个颜色，结果**整个 colors 被换掉**，
其余颜色全丢。改为深合并一层。

用户看到一句没有信息量的提示。`errorMessage()` 统一归一。

### 5.2 `strict: true`（T3.7）

**零成本** —— 改之前先实测过：

```

（无输出，退出码 0）
```

改成 `strict: true` 后仍然 0 error。同时把 `noUnusedLocals`/`noUnusedParameters`
也验证了一遍（`--noUnusedLocals --noUnusedParameters` 同样 0 error），
但**没有开** —— 台账没要求，且开了会牵连未使用的参数（与破坏性变更的边界）。

### 5.3 破坏性变更：无

本轮**没有**改动任何既有公共 API 的签名：

- `useTheme()` **新增**了 `preference` 与 `setPreference` 字段 —— 增字段不是破坏，
  下游解构 `{ mode, toggle }` 仍工作；
- `analyze` 的 `results` 参数从 `any` 收成 `unknown` —— 对调用方是**放宽**不是收紧
  （`unknown` 接受任何值），只有依赖 `any` 的**隐式 any 行为**（比如不标注就当 any 用）
  才会受影响，那种代码本来就该改；
- `onExecute` 的返回类型从 `Promise<any>` 收成 `Promise<unknown>` —— 同上。

### 6.1.1 首轮跑批放跑了 4 条 —— 是**判据不敏感**，不是实现没问题

首轮 15 条里有 4 条「没咬住」。逐条查下来，**全部是判据自己的毛病**：

| # | 放跑原因 | 修法 |
|---|---|---|
| M5 | 断言写的是 `${PROVIDER_DEFAULT_BASE_URL.ollama}` —— **引用了被测常量本身**。常量一改，期望值跟着改 ⇒ 恒绿 | 断言改**字面量**；另加一条「常量表本身是对的」用例把常量钉死 |
| M7 | 断言「200 次创建的 id 互不相同」—— 随机实现下 7 位 base36 几乎不可能碰撞，判据形同虚设 | 改成断言 id 的**结构**（`toast-N` 形状 + N 严格递增） |
| M9 | 断言「clear 后到点不再操作 store」—— 悬挂回调执行时调的是 `removeToast(已移除的 id)`，**对 store 没有可见影响** | 改用 `process.getActiveResourcesInfo()` **直接数挂起的定时器** |
| M10 | 同上 | 同上 |

**这四条如果没跑变异验证，就会一直「绿」下去** —— 它们看上去都在测 A-12，
实际上一个都没测到。这就是「判据必须证明自己咬得住」的意义。

另有一条 `executeAI 遇到未知 provider` 的用例**基线下没注入 fetch**：
基线靠工厂 `throw` 提前退出，走不到网络；但变异一旦让未知 provider 回落成
OpenAI，它就会真的去请求 api.openai.com —— 变异跑批时这条挂了 10 秒才超时。
现已注入桩，并加断言「未知 provider 不该发出任何请求」。

### 6.1.2 变异脚本本身踩的三个坑

1. **heredoc 里的 `\n` 被 shell 展开** ⇒ python 的锚点串与文件实际内容不匹配
   ⇒ 变异**从未真正发生**，而测试因为跑的是上一轮残留的变异版文件而「显示咬住」。
   改法：变异逻辑挪到独立的 python 文件，逐行匹配，不依赖换行转义。
2. **备份目录复用** ⇒ 脚本被中断时 `restore()` 没跑到，备份已被变异版污染
   ⇒ 还原时把变异留在源文件里。改法：备份目录按 run 隔离，且**还原后核对关键行**。
3. **没有超时** ⇒ M2（去掉 AbortController）让「永不 resolve 的 fetch」永久挂起，
   整批卡死。改法：`--test-timeout=10000`，挂起单独算一种「咬住」。

> 第 1 条最隐蔽：**变异没写进去**，和**判据不敏感**，在屏幕上是同一种现象
> （都是「测试没红」）。唯一能分开它们的办法是**还原后核对源文件本身**。

> 变异脚本的三个关键点（都是本会话踩出来的）：
> 1. **每条变异前先还原**（还原写在循环末尾 ⇒ 上一条的失败泄漏到下一条）；
> 2. **定向跑单文件**，不跑全量 —— 第一版跑全量，M1 让 AI 测试去打真实
>    OpenAI 端点，每个用例 30s 超时，一轮跑了 10 分钟没跑完；
> 3. **编译失败不算咬住**，必须看到断言失败。

### 6.2 变异跑批时踩到的另一个坑

变异脚本的备份目录被**后续轮次覆盖**（`restore()` 写的是同一个目录），
第一版跑到一半时备份已经是变异版，**还原时把变异留在了源文件里**。
靠 `grep` 核对关键行才发现。改法：备份目录独立于运行目录，且还原后**必须核对关键行**。
